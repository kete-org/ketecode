## Quick answers

- **How does the extension talk to the agent?** It spawns its own `kete serve --stdio` (never the
  workspace's or PATH's `kete`) and frames the runtime's own web UI (`packages/app`) in a webview
  iframe; there is no separate agent logic in the extension (CLAUDE.md §3, §6).
- **What binary does it run?** The one bundled per platform in `bin/`
  (`packages/kete-vscode/src/binary.ts:43`); `kete.cliPath` overrides it for development only
  (`binary.ts:30-51`).
- **How is the local server secured?** Loopback only, random port (`--port 0`), random per-session
  password via `KETE_PASSWORD` env (`server.ts:104-113`), Basic auth on every request
  (`events.ts:140-142`), plus the server's own `local-guard` Host/Origin checks (see
  `docs/architecture.md` §22, `server/src/kete/local-guard.ts`).
- **What are the two "kept free of `vscode`" halves?** Every `src/*.ts` file except
  `extension.ts`, `mcp-view.ts`, and `server.ts`'s VS Code wiring is plain TS with no `vscode`
  import, so it unit-tests with plain `bun test`; `extension.ts` is the glue that imports `vscode`
  and wires them together. `panel.ts` (below) follows the same pattern.
- **How does the chat panel's "what's new" notices/CLI hint survive a window reload?** `panel.ts`'s
  `dismissNotice`/`dismissCliHint` persist to `context.globalState` under
  `kete.panel.dismissedNotices` (an array, capped at 50, deduped, unknown ids ignored) and
  `kete.panel.cliHintDismissed` (a boolean); `extension.ts` re-derives the full `kete.panel` message
  from that store on every read (`panelState`, `extension.ts:411-418`), so nothing is cached
  in-memory across a reload.
- **Where does the Kete mark come from on VS Code's own chrome (commands, status bar, chat tab,
  terminal)?** A generated icon font, `media/kete-mark.woff`, registered as the `kete-mark` product
  icon (`contributes.icons`, `package.json:41-48`) and referenced as `$(kete-mark)` — every command
  icon that used to be a built-in codicon now uses it (`package.json`'s `contributes.commands`), the
  status bar prepends it (`status.ts:23`, `` `${icon} $(kete-mark) Kete${who}…` ``), and
  `openTerminal`/`mcp-view.ts`'s auth terminal set `iconPath: new ThemeIcon("kete-mark")`
  (`extension.ts:985`, `mcp-view.ts:119`). Generated by `script/icon-font.ts` (not part of the build;
  run by hand when the mark's geometry changes, then commit the output) via a pinned dev tool
  (`fantasticon@4.1.0`, run through `bunx`, not a project dependency) — parses
  `packages/app/src/kete/mark.tsx`'s `MARK_RECTS` (the single geometry source, same regex-based
  parse `test/brand.test.ts` uses) and emits a monochrome glyph (fill color is irrelevant; the font
  extracts outlines only).
- **Where does the chat webview's tab icon come from?** `media/kete-tab-{light,dark}.svg`
  (`extension.ts:227-230`, `panel.iconPath`), also generated by `script/icon-font.ts` from the same
  `MARK_RECTS` — two-tone: brand-fill bars stay the brand violet, ink-fill bars become
  ink-on-paper (light) or paper-on-ink (dark).
- **What does the status bar show for the chat's mode?** `status.ts` `statusBar(…, permissionMode)`:
  nothing for Default, `$(shield) Ask`, `$(zap) Auto`, `$(eye) Plan`, `$(edit) Accept edits`, each with
  an honest tooltip; `extension.ts` `modeOf` accepts all five modes (falls back to the
  `kete.chat.askBeforeEdits`-derived `serverMode`, still only default/ask). The title-bar shield stays
  Ask ⇄ Default (`kete.askBeforeEdits` context = mode is `ask`).
- **Who else writes the session's permission mode besides the title-bar toggle?** As of this task,
  the web app's own chat-panel toggle (`packages/app/src/kete/composer-controls.tsx`'s
  `KeteModeToggle`, `mode.ts` — see the `web-app` and `permissions` cards) is a second writer of
  `kete.permissionMode`, using the same GET-merge-PATCH pattern as `extension.ts:1208-1279`. The
  extension's title-bar shield still re-reads it via `session.metadata.updated` either way
  (`extension.ts:490`), so it follows whichever side changed it.

- **Does it work in Windsurf, Cursor and VSCodium?** Yes, from Open VSX (the forks can't use the
  Marketplace). Nothing assumes Microsoft's VS Code: session links use `env.uriScheme`
  (`sessions.ts`'s `sessionLink` rejects a malformed scheme), the diagnostics tool's description
  names `env.appName` through `editor-tools.ts`'s `editorName()` (cleaned, ≤64 chars, fallback "the
  editor"), sign-in uses a loopback callback (no editor scheme), and there's no proposed API.
  `test/fork.test.ts` guards all of it: no `vscode://`/"VS Code"/Marketplace literal in `src/` code
  (comments excluded), no `enabledApiProposals`/`extensionDependencies`, no "VS Code" in
  `contributes`, and no default keybinding on the forks' AI keys (`Cmd/Ctrl+K/L/I/E`, …). README
  "Using Kete Code in Windsurf, Cursor or VSCodium" has the manual checklist for Windsurf/Cursor.
- **Why is `engines.vscode` still `^1.94.0`?** It must stay at or below every current fork's base
  (October 2026: Windsurf/Devin Desktop 1.126, Cursor 1.128, VSCodium 1.135; sources in
  `docs/tasks/2026-10-05-windsurf/plan.md`). `@types/vscode` is pinned to the same version, so
  typecheck proves every API used exists at the floor; `test/fork.test.ts` keeps them equal and the
  floor ≤ 1.126. Raising the floor needs both bumped together and a check of the forks' bases.
- **Where does the end-to-end suite run?** Locally (`bun run e2e <vsix> [--code <editor CLI>]
  [--assert]`) and in CI: `kete-release.yml`'s `extension-e2e` job (tags and manual dispatch) runs it
  with `--assert` on the linux-x64 `.vsix` in pinned, SHA-256-checked VS Code and VSCodium archives
  under xvfb. Not in `kete-build.yml` (free-minutes budget).

## Purpose

Thin VS Code client for the local `kete serve` runtime: chat panel, editor context, diff review,
account, sessions, MCP servers view, and an editor-diagnostics MCP tool. Must work unmodified in VS
Code forks (Cursor, Windsurf, VSCodium) since it ships to both the Marketplace and Open VSX
(CLAUDE.md §6). Architecture and rationale: `docs/architecture.md` §22 ("IDE Architecture").

## Data flow

1. First chat open (or command) → `Server.connection()` spawns `kete serve --stdio`
   (`server.ts:97-148`) → extension gets `{url, password}`.
2. `chat.ts` builds an iframe pointed at `url` with the password in the fragment
   (`pairingUrl`, never sent to the server) and a nonce-scoped relay script.
3. The web UI (`vscode-host.tsx`) posts `kete.hello`; the relay replies with the current VS Code
   theme (`chat.ts:96-107`) and forwards `fromFrame`/`toFrame` message types only.
4. Editor context: `window.onDidChangeActiveTextEditor`/`onDidChangeTextEditorSelection` →
   `scheduleEditorContext` → `editorContext()` (secret/exclude filtered) → posted as
   `kete.editorContext`; the web UI keeps at most one such chip per composer
   (`vscode-host.tsx:118-121`, `:166-172`).
5. Attention: `EventStream` follows `GET /api/event` independently of webview visibility, feeding
   `reduce()` → status bar text (`status.ts`) and the sessions tree badge.
6. Review: web UI reports the open session via `kete.session`; **Review Changes** fetches
   `GET /api/session/:id/diff`, computes the "before" text (`review.ts:before`), serves it on a
   `kete-before:` read-only scheme, and opens VS Code's diff editor.
7. Editor tools: a loopback HTTP/MCP server starts once (`startEditorTools`, `extension.ts` editor
   tools section) and is (re)registered with the running `kete serve` via
   `PUT /api/experimental/mcp/editor` after every server start (`registerEditorTools`); the runtime,
   not the extension, executes the tool call and applies permissions.
8. Chat panel notices/CLI hint: on `kete.hello` (and after every dismissal), `extension.ts` sends
   `kete.panel` — `panelState()` reads `context.globalState`'s dismissals through `panel.ts`'s
   `loadPanelState`, `platform` from `process.platform === "darwin"`, `defaultMode` from
   `state.serverMode` (`extension.ts:411-421`). The web UI's `vscode-host.tsx` listener updates
   `panel-state.ts`'s signal (setting `host: "vscode"`), which `panel.tsx` renders. Dismissing a
   notice or the CLI hint posts `kete.dismissNotice`/`kete.dismissCliHint`; the extension persists it
   via `panel.ts` and re-sends `kete.panel` to **every** ready webview, not just the one that
   dismissed (`broadcastPanelState`, `extension.ts:425-427`), so two open chat tabs stay in sync.

## Data and APIs used

- CLI subprocesses: `kete serve --stdio --hostname 127.0.0.1 --port 0`, `kete whoami --format json`,
  `kete login`, `kete logout`, `kete debug paths`, `kete sync --status --format json`,
  `kete sync --approve <key> --command <exact>`, `kete mcp auth <key>` (run in a terminal).
- Runtime HTTP API (all Basic-authed with the session password, `events.ts:140-142`):
  `GET /api/event`, `GET /api/session?directory=`, `GET /api/session/:id`,
  `PATCH /api/session/:id`, `GET /api/session/:id/diff`, `GET /api/mcp?directory=`,
  `PUT /api/experimental/mcp/editor?directory=`,
  `POST /api/experimental/mcp/:key/connect|disconnect?directory=`.
- VS Code APIs only (webview, tree views, status bar, terminal, URI handler, diagnostics,
  configuration) — no private/proposed API, per CLAUDE.md §6.
- `context.globalState` (`vscode.Memento`, workspace-scoped): `kete.panel.dismissedNotices` (string
  array), `kete.panel.cliHintDismissed` (boolean) — see `panel.ts`'s `Store` interface.

## Rules that must not break

- Never run a `kete` from PATH; only `binary.ts`'s resolved bundled/`cliPath` binary
  (`extension.ts` header comment, `binary.ts:1-3`).
- Local server: random port + random password per launch, loopback bind, Basic auth on every
  request, host/origin checks in `local-guard` (docs/architecture.md §22).
- The pairing password lives only in the URL fragment, never sent to the server (`chat.ts:11-18`).
- `fromFrame`/`toFrame` are allowlists — a message type not in both lists is dropped by the relay
  (`chat.ts:56-71`); add new bridge messages to both sides and `vscode-messages.ts`'s validators.
- Editor context and diagnostics never include secret-looking paths or `files.exclude` matches
  (`editor-context.ts:8`, `:21-23`; reused by `workspaceDiagnostics` in `extension.ts`).
- Editor-tools MCP server: exact loopback `Host`, no `Origin` header, and a timing-safe bearer-token
  compare (`editor-tools.ts:109-117`); it deliberately does not expose terminal output (may hold
  secrets, no redaction layer yet).
- `insideWorkspace` (`status.ts:57-63`) must gate every workspace-relative path a message provides,
  to prevent path traversal outside the workspace folder.
- Public VS Code API only, `extensionKind: ["workspace"]` — must behave the same in VS Code forks.
- Permission mode ("ask"/"default") only ever narrows behavior; it's read by
  `core/src/kete/permission-mode.ts` on the `evaluate` hook and never loosens a denial
  (docs/architecture.md §22).
- `panel.ts`'s notice text is never trusted as HTML on the web-UI side — `panel.tsx` renders backtick
  spans as `<code>`, everything else as plain text, never `innerHTML` (see the `web-app` card); adding
  a notice with markup-looking text must not become executable markup.
- `dismiss()` only records ids that name a real entry in `NOTICES` and caps the list at 50
  (`panel.ts:44-48`) — an unbounded or unknown-id-accepting dismissal list would let a stale/foreign
  webview grow `globalState` without limit.

  (`bun run build --single --skip-install` in `packages/cli`) copied to `bin/kete`, then
  `bunx --bun @vscode/vsce@4.0.0 package <ver> --target <t> --no-dependencies
  --allow-missing-repository`. CI: `kete-release.yml` `extension-e2e` (VS Code + VSCodium); see

## Gotchas

- `server.ts`, `binary.ts`, `chat.ts`, `events.ts`, `editor-context.ts`, `editor-tools.ts`,
  `mcp.ts`, `reference.ts`, `review.ts`, `sessions.ts`, `settings.ts`, `status.ts` are deliberately
  free of the `vscode` module — don't import it there, or `bun test` on that file breaks.
- `settings.ts:10` imports `jsonc-parser/lib/esm/main.js` directly (not the package's default UMD
  entry) because the UMD build `require`s its own files at runtime, which the bundle can't resolve;
  `test/bundle.test.ts` is what catches a regression here.
- `Server` restarts mean a new port *and* password on every crash-recovery; `onStatus`'s `running`
  branch reconnects every open webview and re-registers editor tools — don't assume a connection
  stays valid across a restart.
- `editor-tools.ts`'s `authorized()` checks `headers.host === "127.0.0.1:<port>"` exactly; a
  forwarded/rewritten Host header will be rejected by design.
- MCP approvals are never written by `mcp-view.ts` itself — `approve()` only *displays* the exact
  command and calls `kete sync --approve --command <exact>`, which itself refuses if the command
  changed; don't shortcut this by writing config directly.
- `editorContextFollows` in the e2e depends on the web UI posting `kete.editorContextApplied`;
  `KeteVSCodeBridge` posts it both on a change and when it mounts with a file the shell already
  kept (`vscode-host.tsx`) — the mount case was missing until VSCodium's slower composer mount
  exposed it. Keep both paths if the bridge changes.
- `review.ts`'s `before()` throws if a non-whole-file patch's context doesn't match the file on disk
  (`review.ts:74`) — that's deliberate ("the file changed since this turn"), not a bug to silence.
