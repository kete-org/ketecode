# Handoff: Enterprise runtime P3 — GitLab self-managed provider and publisher

## 2026-10-09 implementer (Claude)
- Done: see result.md. PR kete-org/ketecode#26.
- Decisions:
  - **The publisher is pure Go.** The runner image is distroless, so there is no git binary.
    Git smart HTTP and packs are ported from the platform's Harness Code client
    (`internal/gitproto`).
  - **The push is one create command** (zero old id) with a pack the publisher builds itself on
    the job's base. An ambiguous answer is read back.
  - **Base binding.** The controller resolves `base_ref` with the job's own read credential
    before starting the pod, and hands the commit to the publisher (`--base-sha`). The job's
    recorded base must equal it. After a controller restart that commit is unknown (`none`): the
    publisher then accepts only a base on the base branch (merge base), and logs it.
  - **Protection.** For both the base and the default branch, GitLab's `can_push` for the writer
    must be false (ADR 0021 rule 8, GitLab form). A Maintainer writer usually fails it, so the
    minter (a Maintainer) and the writer (Developer) are separate tokens.
  - **Check order follows the platform's `decidePush`:** the outbox's own errors, then bundle
    validation, then GitLab (base, protection, branch), then the base tree, then the push.
  - **Mapping to job-host-v2's reason table:**
    - validator refusals and base-tree conflicts → `refused/bundle_invalid`; a base symlink
      touched → `refused/symlink`;
    - a base not on the base branch, or not the controller's resolved commit →
      `refused/bundle_invalid`;
    - a missing or foreign manifest → `failed/publisher_failed`;
    - unknown protection → `failed/protection_unknown` (job-host-v2 lists it under `failed`; the
      platform's GitHub path refuses it).
  - **MR text is the platform's fixed template**, not the spec's "local summary": ADR 0021
    rule 9 keeps model text and mentions out of PRs.
  - **The outcome travels as the publisher container's termination message.** The controller
    already reads pod status and gets no new RBAC for it.
  - **The writer Secret is the named exception.** The enterprise creates it in the jobs
    namespace. The controller can't `get` Secrets there, a policy forbids it to
    create/update/delete publisher Secrets, only publisher pods may mount them, and no pod may
    take any Secret through `env.valueFrom`/`envFrom`.
  - **Publisher pods are pinned by admission:** the runner image, `kete-job-host publish` with
    its exact flag layout, volumes by name at fixed mount paths, no subPath, hooks, probes,
    workingDir or custom termination path. Their configuration (GitLab URLs, proxy, writer
    Secret names) is a Helm-rendered ConfigMap the controller can't touch.
  - **Clone tokens are named `kete-job-<release>-<machine>`.** The sweep touches only its own
    instance's tokens, never tokens minted less than 5 minutes ago.
  - **Authorization must come from a desired state accepted in the last 2 minutes.**
    `publishing` machines are exempt from the job deadline killer, bounded by the hold time and
    the publisher's own deadline.
  - **A `failed` publish keeps its outbox** until hold expiry, for the operator. Every other
    outcome deletes it.
  - **Bundle vectors.** The platform holds none, so `testdata/bundle-v1` was generated by running
    the platform's `validateBundle` (`generate.sh <platform checkout>`, records the platform
    commit).
- **Not proven / open (needs action):**
  - **A real GitLab self-managed** (CE in a container, then an enterprise instance). Check:
    - project access token minting and revocation;
    - `can_push` semantics with the protected-branch settings the README recommends;
    - protocol v2 `filter blob:none` fetch by SHA (Gitaly sets `allowFilter`);
    - the create-only push answer for an existing ref;
    - the draft prefix;
    - merge_base with SHAs.
  - **Kata:** publisher pods (and `seccompProfile: RuntimeDefault`) have not run in a
    VM-isolated pod.
  - **Platform:**
    - adopt `testdata/bundle-v1` as a contract vector set (the copy here becomes byte-for-byte
      of the platform's);
    - P4b records `publish` → `push_status`;
    - P4b sends `authorized` only after `finish`.
  - Audit and proxy-log shipping to an enterprise sink (spec §3, §4.5) is not built; the
    publisher doesn't read `audit.jsonl`/`proxy.jsonl`.
  - Orchestration publish kinds (platform PR #79) are not built; `publish.Request` and the
    outcome mapping are the seam.
  - The released runner image must ship `/usr/local/bin/kete-job-host`: admission pins that path.
  - A controller restart loses the resolved base commit, so the publisher falls back to the
    ancestor rule (logged). Persisting it (state or a PVC label) would close that.
  - Two runner instances with the same release name sharing a GitLab project would sweep each
    other's tokens. Release names must be unique per project.

## 2026-10-09 implementer (Claude) — independent security review round
- Fixed on the branch:
  - **S1:** `cloneMode: static` is the recommended default. `minted` needs `acceptMinterRisk: true`
    (the chart and `config.Parse` both refuse it otherwise). The README, cards and parent spec
    state that writer isolation against a compromised controller holds only in static mode, and
    recommend a dedicated minter bot.
  - **S2:** an existing merge request is reused only if it is from and to this project, from the
    job branch into the base, a draft, and its author is the writer (`GET /user`); otherwise the
    publisher opens its own. Tested with fork, other-author, other-target and non-draft MRs in the
    fake.
  - **S3:** the controller's resolved base SHA travels in the job Secret
    (`local.repository.base_sha`). The entrypoint fetches exactly that commit (`gitops.CloneAt`) and
    fails `clone`/`verify` with code `base_unavailable` otherwise. In the publisher a base mismatch
    is `failed/provider_error`: the job-host-v2 reason table has no precise reason for it.
  - **S4:** the publisher refuses `.gitlab/` paths and the project's `ci_config_path`
    (`refused/bundle_invalid`). The README lists what `[skip ci]` doesn't stop on GitLab.
  - **Nits:**
    - publisher pods pinned further: no hostAliases or dnsConfig, dnsPolicy default, runAsUser
      65532, allowPrivilegeEscalation false, terminationMessagePolicy File;
    - job pods can't project the `kete-publisher` ConfigMap;
    - the commit date is clamped to ±1 day of now;
    - gitproto server messages redact GitLab token shapes;
    - manifest refusals are logged as a code only;
    - an unreadable publisher creation time counts as timed out;
    - the sweep comment is corrected (`clone_done` isn't persisted).
- **Platform follow-up:** add `.gitlab` to the platform validator's `CI_DIRS` (and regenerate
  `testdata/bundle-v1`). Until then the runner's publisher is stricter than the platform's
  validator there.
