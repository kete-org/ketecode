# Spec: Cloud job egress: nftables rules and the TLS-terminating proxy (ADR 0019 rule 4)

- Task: `docs/tasks/2026-09-30-job-egress` · Size: large · Created: 2026-09-30
- Status: built and reviewed (2026-09-30)

## Goal
Inside a cloud-job container, nothing reaches the network except through one proxy that allows
exactly the hosts each phase needs, for exactly the user that needs them — the egress half of
platform ADR 0019 rule 4 (kete-code-platform `docs/jobs.md` §8 item 2). Piece B of the container
image work (umbrella notes: `docs/tasks/2026-09-30-job-image/`); the entrypoint (piece C) installs
and supervises it.

## Scope
- **Go module** next to the root helper (user decision: Go), e.g. `packages/kete-egress/` or a
  second binary in `packages/kete-root-helper/` — the plan decides, with the reason.
- **The proxy** runs as its own `proxy` user:
  - listens on three privileged loopback ports — A (`kete` user), B (tool user), R (root) — and
    knows which user each port serves;
  - accepts HTTP `CONNECT host:443` and terminates TLS for every allowed host with a per-VM CA it
    generates at start-up (private key readable only by the proxy user; the CA certificate written
    where the entrypoint installs it into the users' trust stores);
  - allows a connection only when the CONNECT host, the TLS SNI and every request's
    `Host`/`:authority` are the same allowlisted name for that port and the current phase; it
    resolves and connects to that name itself and verifies the upstream against the system roots —
    never routes by a client-supplied `Host`;
  - per-phase, per-port exact-host allowlists (clone, agent, report) given by the entrypoint; the
    phase changes only on an instruction from root (e.g. a root-only control socket);
  - package registries: GET/HEAD only, a path-shape allowlist, no query string or body, path ≤ 1 KB,
    at most 20,000 requests per job;
  - a log line per request (phase, user/port, method, host, path cut to 256 B, status, bytes — never
    headers or bodies), root-owned, capped at 10 MB; when full, further requests are refused.
- **The firewall** (nftables, `inet` family, IPv4 and IPv6), generated by the same module and
  applied by the entrypoint as root: only the proxy user may reach TCP 443 outbound and DNS; the
  `kete` user may reach only port A on loopback; the tool user only port B and loopback ports
  ≥ 1024 (its own listeners); root only port R; everything else dropped, including Fly's private
  network and the metadata service. If the rules can't be installed, it's an error (the entrypoint
  aborts before `claim`).
- Allowlists are configuration from the entrypoint (the platform's hosts from `claim`: gateway,
  platform API, storage host; GitHub hosts; the registry list) — nothing hard-coded except the
  registry path shapes.
- **Tests:** Go unit tests (allowlist matching, SNI/Host checks, registry rules, log cap, phase
  switching); an integration test in a privileged container with local fake upstream HTTPS servers
  (their own test CA), fake DNS, and real nftables rules and users — showing allowed requests pass
  and every forbidden case is refused (wrong port for the user, host not allowed in the phase, SNI ≠
  Host, domain fronting, registry POST/query/oversized path, direct connection bypassing the proxy,
  DNS from a non-proxy user, log full). Run locally in Colima and in a path-filtered CI workflow.

## Out of scope
- The entrypoint itself (piece C), the image and publishing (D), runtime changes (A).
- Installing the CA into trust stores and starting/supervising the proxy (the entrypoint does it;
  this task provides the pieces and documents how).

## Acceptance criteria
- [x] AC1: Allowed requests for each phase and port reach their upstream over TLS terminated by the
  proxy's CA, with the upstream verified.
- [x] AC2: Refused: a host not allowed for that phase/port; SNI or `Host` differing from the CONNECT
  host; a registry request that isn't GET/HEAD, has a query or body, or a path over 1 KB; more than
  the request cap; any request once the log is full.
- [x] AC3: With the nftables rules applied, each user can reach only its own proxy port; direct
  outbound connections and DNS from non-proxy users fail; IPv6 is covered.
- [x] AC4: The log records each request without headers or bodies and never exceeds 10 MB.
- [x] AC5: `go vet`, unit tests, the privileged integration suite (locally ×3 and in CI) pass;
  `upstream:check`, lint.

## Risks and constraints
- **Security-critical:** the proxy and the rules are the job's only network boundary; a guest-root
  escape defeats them (ADR 0019), so short credential lifetimes remain the real bound.
- nftables must work in Fly Machines' kernel and in CI's runners — verify empirically (the task's
  integration test is the check).
- Package managers must work through a TLS-terminating proxy with a custom CA (`npm`, `pip`, `cargo`,
  etc. read different CA settings) — the entrypoint/image sets them; this task documents the
  variables.
- CI minutes: the new workflow is path-filtered.
